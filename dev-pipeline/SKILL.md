# 通用开发流水线

工作流是一条**流水线**：起点是用户的输入——先弄懂请求、定模式，再沿主干 Stage 1→5（理解上下文 → 方案 → 实现 → 验证 → 交付）推进；调试、Review、TDD、文档、重构准备等是挂在主干上的**分支**。需要加载 `references/` 细节时，先读 `references/resource-map.md`，再按地图选择具体文件。

## 关键边界

- 遇到 `plan only` / `review only` / `explain only`，本轮就是只读任务：不创建任务记录，不改文件，不 stage，不 commit。
- 提交保持显式授权：只有用户明确要求提交，或交付 diff 后确认提交，才按 repo 约定 commit；push 同理。
- 任务记录只用于多步实现、长任务恢复、切片、回流和已搁置阻塞；只读任务和单文件低风险任务默认跳过。
- 单文件低风险任务走轻量路径：不启动子代理、不切片、不建任务记录；需要解释时，用一句话说明跳过原因。
- 删除、覆盖、迁移、部署、发送消息、批量写入、联网改状态、付费调用等高副作用操作，必须先停下拿到明确确认。

## 理解输入与入口判定（流水线起点）

流水线从用户输入开始：先理解请求，再定模式，然后进 Stage 1（理解上下文）。

**先理解输入：**

- 复述你理解的需求和目标，确认抓对了要做什么。
- 请求本身有歧义、缺关键信息、或多种合理解读会导向不同实现时，先问一个会改变实现路径的关键问题；能从代码/文档判断的细节直接查证后推进。
- 从请求里抽出约束：范围、明确的不做项、`plan only`/`review only` 这类模式约束、deadline 或非功能要求。
- 没澄清就推进时，记下做的关键假设和"假设错了要回头改什么"，交付时一并说明，方便用户纠偏。

**再定模式：**

按交付物定模式（按序看，命中即定）：

- `plan only`/`review only`/`explain only`，或交付物是判断、方案、review、风险评估、扫描结果 → **分析模式**：只输出判断建议，不改文件，止于 Stage 2。
- 单命令、纯概念、无需 repo 的一步问答 → **off-ramp**：直接答，不进流水线。
- 交付物是改好的代码/文档/修复的行为 → **实现模式**：走完 Stage 5。
- 不清楚 → 默认分析模式：先复述交付物和建议路径，不写文件。

边角规则（重构默认先出方案、上轮写入建议被接受、何时停下等确认）见 `references/entry-modes.md`。

## 主干流水线

**阶段衔接原则**：每个 Stage 收尾时，在回复里显式说明"本阶段结论 + 下一步去哪 + 要做什么"，让用户清楚流水线走到哪、接下来去哪。推进不等于自动执行——是否前进仍受入口判定的模式和关卡约束（分析模式止于 Stage 2；高风险/破坏性/需确认时停下等用户）。

流水线允许回流：把回流当作保护交付质量的机制；任何 Stage 发现上游判断错了，显式**退回**并说明原因。常见回边——实现中发现上下文不足或方案站不住 → 退回 Stage 1/2；验证发现是需求/方案理解错（不是实现 bug）→ 退回 Stage 2 或回去找用户重新澄清。任务记录启用时，过 Stage、回流、搁置阻塞要顺手更新（见跨阶段规则）。
同一对 Stage 间回流超过 2 次就停下，别继续震荡：总结卡点，给用户选项（换方案 / 放宽约束 / 升级到需要人介入）。

### Stage 1 · 理解上下文

- 先读当前 repo 的约束来源：repo instruction files、README、docs、ADR、TODO、用户点名的规范文件。
- 改代码前收集上下文：现有工作流分支、相邻实现、service/API contract、数据流、控制流、命名模式、测试或验证入口。
- 涉及状态流或用户动作时，沿事件逐个做 guard/effect 审查：允许状态、禁止状态、no-op 行为、missing guard、side effect owner、terminal behavior，以及 tests/docs 是否覆盖当前行为。
- 重构、迁移、架构调整这类高风险工作，按 `references/refactor-prep.md` 的清单准备。
- **→ 下一步**：上下文足够后，推荐进入 Stage 2，并预告将提的方案要点；上下文还有缺口时，先说明缺什么、要去哪找。

### Stage 2 · 方案与关卡

- 大改前先分享方案：当前行为、目标行为、改动范围、保持不变的行为、风险、验证计划。
- 任务偏大时，方案里就把它切成纵向片：每片是一条薄的端到端改动，独立走一遍 Stage 3-5 并拿反馈，再做下一片；不要一趟把整个 feature 摊开实现到底。
- 多页面、多入口或多外部状态任务必须列出纵向片，例如 `contract + helper`、`入口 A 保存/展示`、`入口 B 确认/回滚`、`review/detail 展示`；每片要有对应验证入口，或说明为什么合并验证。
- **自动计划 review**：方案命中子代理委派触发条件（见跨阶段规则·子代理委派）时，默认按 `references/delegation.md` 的「计划 review 子代理委派」fan-out 多视角 review 子代理，主线程至少汇总一份计划 review 结果后再过关卡；如果任务强耦合、不能等待或子代理工具调用失败，必须记录原因并做本地第二轮自审。窄范围低风险方案不 fan-out，主线程自审即可。
- **关卡**：分析模式在此交付方案（含 review 汇总）即止，不写文件。实现模式只有在没有触发等待条件时，才在简短方案后继续推进到 Stage 3。
- **→ 下一步**：分析模式在此收尾，推荐用户确认方案或挑选路径；实现模式且无等待条件时，推荐进入 Stage 3 并说明第一步改什么。

### Stage 3 · 实现

- 范围以本轮目标为边界：只纳入完成目标必需的相邻流程、入口校验、交互策略、持久化、运行期副作用和数据模型变化。
- 实现规则（单一事实来源、状态机建模、phase boundaries、命名等）见 `references/implementation.md`。
- 走分支时按对应 reference 调整本阶段节奏：调试 → `references/debugging.md`；TDD → `references/tdd.md`；文档 → `references/docs.md`。
- **→ 下一步**：改动完成后，推荐进入 Stage 4，并预告将按验证选择矩阵跑哪些验证项。实现中发现上下文不足或方案站不住时，优先退回 Stage 1/2，保护后续改动不建立在错误假设上。

### Stage 4 · 验证

- 修改后走检查清单：命名、重复状态、非法状态、数据来源是否唯一、side effect owner、event guard、boolean 前缀、范围是否漂移、可读性、验证是否足够。
- 按下方**验证选择矩阵**执行；没做的验证要明确说。
- 高风险改动（命中子代理委派触发条件）默认 fan-out 独立审查——按发现协议选匹配的（如 reviewer / security-auditor；涉及架构或跨模块边界改动时加 architect-reviewer），多份发现项用 knowledge-synthesizer 汇总；未启动时须写明理由。
- **→ 下一步**：验证通过后推荐进入 Stage 5 交付检查；验证暴露问题时，先分清是实现 bug（退回 Stage 3 修）还是方案/需求理解错（退回 Stage 2，或回去找用户重新澄清），并说明退回原因，别在错方案上反复改代码。

### Stage 5 · 交付检查

- 检查最终 diff。
- 搜索旧命名、旧 boolean flags 和重复状态。
- 确认没有 revert、覆盖或 stage 用户已有改动。
- 确认新文件名和 exported symbols 有明确作用域但不冗余。
- 跑 `git diff --check`。
- 按验证选择矩阵执行必要验证并记录未验证项。
- 确认该启动的子代理都已启动，或记录了不启动的理由（子代理委派关卡兜底）。
- 最终回复说明改了什么、验证了什么、还有什么没验证；验证项要写明实际命令或目标范围，例如定向 lint/typecheck/test 覆盖了哪些文件或行为。
- 仅在用户明确要求提交，或交付 diff 后用户确认提交时，才按 repo 既有 commit 约定提交自己这轮的改动；逻辑独立分多个提交，message 讲清 why 而非复述 diff；**不 push，除非用户明确要求**。
- **→ 下一步**：流水线终点。如有后续建议（残余风险、可拆出的跟进项），提出但不自动执行。交付后若被用户纠正或反馈，按 `references/rule-distillation.md` 把它沉淀成持久规则，别只当一次性修补。

## 分支模式（按触发从主干切入）

按触发词切入对应分支，只加载需要的 reference，不走全程主干以外的内容：

- **代码审查** — 触发：`review`、`code review`、`看 diff`、`审这个 PR`。切入 Stage 1→2，只读，不进 Stage 3。加载 `references/code-review.md`。
- **调试** — 触发：报 bug、行为异常、排查、`debug`。切入 Stage 1→3。加载 `references/debugging.md`。
- **测试驱动** — 触发：`TDD`、`test-first`、`red-green-refactor`。改写 Stage 3 节奏。加载 `references/tdd.md`。
- **文档** — 触发：改文档、更新 README/ADR/技术说明。走轻量 Stage 1/4。加载 `references/docs.md`。
- **重构准备** — 触发：高风险重构/迁移/架构调整。Stage 1 前置。加载 `references/refactor-prep.md`。

（子代理委派是任意阶段都能用的横切能力，见下方「跨阶段规则 · 子代理委派」。）

## 跨阶段规则（全程适用）

### 沟通方式

- 遵守当前系统、用户和 repo 的语言政策；没有明确约定时，保持简洁清晰。
- 开门见山，先给结论，再解释机制和取舍。
- 用真实用户场景说明问题为什么重要，再解释技术机制。
- 不要把用户拉进不必要的输入请求；能从代码和文档判断时直接推进。
- 如果方案有风险，说明具体故障模式：什么会坏、谁承担代价、什么时候爆发。

### 项目适配

- 不要预设框架或项目技术栈。
- 如果当前 repo 有本地说明、框架文档、团队规范、架构决策记录或项目约定，优先加载并遵守它们。
- 如果没有额外项目规范或专用工具，回到轻量流程：读现有代码、依赖配置、类型定义、测试入口和相邻实现，不要因此阻塞。
- 涉及外部库、框架、SDK、协议或 API 签名时，先查当前项目依赖、类型定义、官方文档或用户指定来源。
- API contract 以实际 types、services、schemas 和调用点为准。不要发明字段、状态、权限规则或配置对象。
- 跨模块边界先按当前项目既有实践判断，例如路由、状态管理、UI、HTTP、数据库、CLI、队列或其它适用边界；不要套用别的 repo 的习惯。

### 工作区保护

- 在 git repo 里改文件前，先看 `git status --short`；把已有 modified/untracked 文件当作用户或其他流程的工作。
- 如果目标文件已经 dirty，先读当前 diff，再叠加本次修改；不要覆盖、格式化或回滚无关改动。
- 未经用户明确要求或确认，不 stage、commit、push；不要覆盖或回滚用户已有的无关改动。
- 最终检查只解释本次自己改动的范围；无关 dirty 文件不当作自己的成果。

### 阻塞处理

- 撞到阻塞（等用户/产品决策、依赖的接口未就绪、测试环境不可用、需他人配合）时，把阻塞显式化：说清阻塞点、它卡住的决策，以及解除后回到哪个 Stage。
- 能在阻塞外推进的部分先做，并标出哪些被 park、解除后要回到哪一步；整条都被卡死时停下等解除，不用猜测填补。

### 任务记录

- 只有实现模式的多步任务、长任务恢复、切片/回流/搁置阻塞，或用户允许记录时才启用任务记录；`plan only` / `review only` / `explain only`、off-ramp 和单文件低风险任务默认不创建。
- 启用任务记录时，先列 `.dev-pipeline/`；有本任务的记录就优先读回并接续，保留之前的模式判定、假设和已搁置阻塞；没有再新开 `.dev-pipeline/<date>-<short-slug>.md`。
- 跟着流水线事件更新记录——过 Stage、回流、搁置阻塞、记关键假设、切完一片，供回流、切片之间、上下文压缩后捡起来。模板和规则见 `references/scratch-pad.md`。
- 只依赖写文件，不依赖 host 的 task 工具；ephemeral，`.dev-pipeline/` 进 `.gitignore`，绝不 commit。
- 入口判定走 off-ramp（单命令/纯概念/一步问答）不进流水线，自然不需要。

### 子代理委派

- 子代理委派是横切能力，任意阶段/分支都能用。命中触发条件时**默认启动对应子代理（spawn subagents / delegate）作为质量门槛**：让子代理承担独立审查/验证，主线程专注整合、取舍和最终交付；只有明确命中跳过条件或异常降级条件时才留在主线程。
- **触发条件**（命中任一即默认启动子代理）：涉及多模块、状态流、外部 contract、side effects、权限/数据流、用户可见行为；有可独立审查的 diff；或可拆成边界清楚的只读审查/独立验证。
- **量级门槛**（防止反射式过度启动）：要够分量才算命中——多模块=改动跨>1 个模块边界（不是在一个模块里调另一个 API）；外部 contract=改了 public 接口/schema（不是内部实现）；用户可见行为=改了流程/失败模式/输出格式（不是改个文案 label）；side effects=异步/网络/持久化（不是同步内存操作）。够不着门槛的窄改动留主线程，避免为流程形式启动子代理。
- **跳过须交代**：够不着量级门槛时，一句话或任务记录里说明不启动理由即可（如单文件低风险、强耦合设计判断、需连续用户交互）；命中触发条件却不启动子代理时，必须说明工具失败、项目配置禁止或安全边界冲突。低风险任务说明未命中门槛即可，不跑发现协议。
- 判据细节、只读边界、发现协议（怎么从 `prompts/` 选模板）、子代理启动与异常降级，见 `references/delegation.md`。

### 验证选择矩阵

- 行为改动：优先跑覆盖该行为的定向测试；没有测试时做手动路径验证并说明缺口。
- 前端可视行为：浏览器冒烟验证不是默认硬要求。只有本地路由、登录态、测试数据和浏览器工具都可用，且验证成本合理时才执行；否则用更窄验证替代，并明确列出未验证的具体交互。
- 类型、schema、API contract 改动：跑 typecheck 或最接近的静态检查，并检查调用点。
- `build` 和全量检查属于高成本验证；只有构建 artifact / 打包产物是本次交付物、用户明确要求、或没有更窄验证能覆盖关键编译风险时才跑，并说明为什么值得付出成本。其它改动默认选择定向测试、typecheck、lint 或手动路径验证。
- 文档改动：用事实来源对照关键命令、路径、术语和示例，不用为了纯文档默认跑全量测试。
