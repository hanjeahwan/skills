# 通用开发流水线

工作流是一条**流水线**：先过入口判定决定模式，再沿主干 Stage 1→5 推进；调试、Review、TDD、文档是挂在主干上的**分支**，按触发词从对应阶段切入，详细规则在 `references/` 里按需加载。

## 入口判定（先定模式，再进流水线）

- 当任务需要理解当前 repo、修改文件、审查 diff、调试行为、设计重构、补测试、更新技术文档或交付验证结果时，使用完整流水线。
- 如果用户只要单条命令输出、纯概念解释、简单路径查找，或不需要 repo 上下文的一步回答，直接完成，不要套完整流程。
- 如果用户明确说 `plan only`、`review only`、`explain only` 或类似约束，严格保持该模式；除非用户追加要求，不要改文件。
- 写入文件前先判断本轮用户要的交付物。如果交付物是判断、解释、扫描结果、方案、review、风险评估、影响面或取舍建议，进入**分析模式**，只输出判断和建议，不改文件，在 Stage 2 结束。
- 如果交付物是已修改的代码、已更新的文档、已生成的文件或已修复的行为，进入**实现模式**，走完 Stage 5。
- 如果交付物不清楚，默认进入分析模式：先复述你理解的交付物和建议路径，不写文件。
- 对重构、迁移、架构调整这类高风险工作，如果用户没有明确要求交付修改后的文件或行为，默认先交付方案；用户确认方案或要求写入后，再进入实现模式。
- 如果上一轮已经给出具体写入建议，本轮用户明确接受或要求继续，视为交付物变成修改后的文件，进入实现模式。
- 只有进入实现模式，且任务明显需要代码或文件修改时，才默认推进到实现和验证；需求不清、操作有破坏性、权限/数据风险高，或用户明确要求先确认时，先停下来等用户决定。

## 沟通方式

- 遵守当前系统、用户和 repo 的语言政策；没有明确约定时，保持简洁清晰。
- 开门见山，先给结论，再解释机制和取舍。
- 用真实用户场景说明问题为什么重要，再解释技术机制。
- 不要把用户拉进不必要的输入请求；能从代码和文档判断时直接推进。
- 如果方案有风险，说明具体故障模式：什么会坏、谁承担代价、什么时候爆发。

## 主干流水线

**阶段衔接原则**：每个 Stage 收尾时，在回复里显式说明"本阶段结论 + 推荐进入的下一阶段 + 下一步要做什么"，让用户清楚流水线走到哪、接下来去哪。推荐下一阶段不等于自动执行——是否推进仍受入口判定的模式和关卡约束（分析模式止于 Stage 2；高风险/破坏性/需确认时停下等用户）。

### Stage 1 · 理解上下文

- 先读当前 repo 的约束来源：repo instruction files、README、docs、ADR、TODO、用户点名的规范文件。
- 改代码前收集上下文：现有工作流分支、相邻实现、service/API contract、数据流、控制流、命名模式、测试或验证入口。
- 涉及状态流或用户动作时，沿事件逐个做 guard/effect 审查：允许状态、禁止状态、no-op 行为、missing guard、side effect owner、terminal behavior，以及 tests/docs 是否覆盖当前行为。
- 重构、迁移、架构调整这类高风险工作，按 `references/refactor-prep.md` 的清单准备。
- **→ 下一步**：上下文足够后，推荐进入 Stage 2，并预告将提的方案要点；上下文还有缺口时，先说明缺什么、要去哪找。

### Stage 2 · 方案与关卡

- 大改前先分享方案：当前行为、目标行为、改动范围、保持不变的行为、风险、验证计划。
- **自动计划 review**：方案命中高风险判据（多模块、状态流、外部 contract、side effects、权限/数据流、用户可见行为）时，默认按 `references/delegation.md` 的「计划 review 委派」fan-out 多视角 review 子代理，主线程汇总后再过关卡；窄范围低风险方案不 fan-out，主线程自审即可。
- **关卡**：分析模式在此交付方案（含 review 汇总）即止，不写文件。实现模式只有在没有触发等待条件时，才在简短方案后继续推进到 Stage 3。
- **→ 下一步**：分析模式在此收尾，推荐用户确认方案或挑选路径；实现模式且无等待条件时，推荐进入 Stage 3 并说明第一步改什么。

### Stage 3 · 实现

- 保持范围窄。不要把相邻流程、入口校验、交互策略、持久化、运行期副作用、数据模型扩展一起带进来，除非任务明确包含。
- 实现规则（单一事实来源、状态机建模、phase boundaries、命名等）见 `references/implementation.md`。
- 走分支时按对应 reference 调整本阶段节奏：调试 → `references/debugging.md`；TDD → `references/tdd.md`；文档 → `references/docs.md`。
- **→ 下一步**：改动完成后，推荐进入 Stage 4，并预告将按验证选择矩阵跑哪些验证项。

### Stage 4 · 验证

- 修改后走检查清单：命名、重复状态、非法状态、数据来源是否唯一、side effect owner、event guard、boolean 前缀、范围是否漂移、可读性、验证是否足够。
- 按下方**验证选择矩阵**执行；没做的验证要明确说。
- **→ 下一步**：验证通过后推荐进入 Stage 5 交付检查；验证暴露问题时，退回 Stage 3 修复并说明退回原因。

### Stage 5 · 交付检查

- 检查最终 diff。
- 搜索旧命名、旧 boolean flags 和重复状态。
- 确认没有 revert、覆盖或 stage 用户已有改动。
- 确认新文件名和 exported symbols 有明确作用域但不冗余。
- 跑 `git diff --check`。
- 按验证选择矩阵执行必要验证并记录未验证项。
- 最终回复说明改了什么、验证了什么、还有什么没验证。
- **→ 下一步**：流水线终点。如有后续建议（残余风险、可拆出的跟进项），提出但不自动执行。

## 分支模式（按触发从主干切入）

按触发词切入对应分支，只加载需要的 reference，不走全程主干以外的内容：

- **代码审查** — 触发：`review`、`code review`、`看 diff`、`审这个 PR`。切入 Stage 1→2，只读，不进 Stage 3。加载 `references/code-review.md`。
- **调试** — 触发：报 bug、行为异常、排查、`debug`。切入 Stage 1→3。加载 `references/debugging.md`。
- **测试驱动** — 触发：`TDD`、`test-first`、`red-green-refactor`。改写 Stage 3 节奏。加载 `references/tdd.md`。
- **文档** — 触发：改文档、更新 README/ADR/技术说明。走轻量 Stage 1/4。加载 `references/docs.md`。
- **重构准备** — 触发：高风险重构/迁移/架构调整。Stage 1 前置。加载 `references/refactor-prep.md`。
- **委派** — 触发：涉及多模块/并行/独立验证。任意阶段。加载 `references/delegation.md`。

## 跨阶段规则（全程适用）

### 项目适配

- 不要预设框架或项目技术栈。
- 如果当前 repo 有本地说明、框架文档、团队规范、架构决策记录或项目约定，优先加载并遵守它们。
- 如果没有额外项目规范或专用工具，回到轻量流程：读现有代码、依赖配置、类型定义、测试入口和相邻实现，不要因此阻塞。
- 涉及外部库、框架、SDK、协议或 API 签名时，先查当前项目依赖、类型定义、官方文档或用户指定来源。
- API contract 以实际 types、services、schemas 和调用点为准。不要发明字段、状态、权限规则或配置对象。
- 跨模块边界先按当前项目既有实践判断，例如路由、状态管理、UI、HTTP、数据库、CLI、队列或其它适用边界；不要套用别的 repo 的习惯。

### 工作区保护

- 在 git repo 里改文件前，先看 `git status --short`；把已有 modified/untracked 文件当作用户或其他流程的工作。
- 如果目标文件已经 dirty，先读当前 diff，再叠加本次修改；不要覆盖、格式化或回滚无关改动。
- 不要 stage、commit、push，除非用户明确要求。
- 最终检查只解释本次自己改动的范围；无关 dirty 文件不当作自己的成果。

### 验证选择矩阵

- 行为改动：优先跑覆盖该行为的 targeted tests；没有测试时做手动路径验证并说明缺口。
- 类型、schema、API contract 改动：跑 typecheck 或最接近的静态检查，并检查调用点。
- 构建 artifact 或打包产物是本次交付物时：才跑 `build` 验证 artifact 是否能生成；其它改动默认不跑 `build`。
- 文档改动：用事实来源对照关键命令、路径、术语和示例，不用为了纯文档默认跑全量测试。
