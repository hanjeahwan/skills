# 可执行指令审查

指令文档的每一句都要指导读者「做什么 / 是什么 / 何时做」。揪出只描述文档自身、不产生动作的句子，改写成正向可执行指令，循环到一次完整扫描零命中。

## 审查—改写循环

```
扫描 → 标记命中 → 改写成正向动作 → 重新扫描 → 零命中才停
                          └──── 改写可能引入新的自述 ────┘
```

## 模式

- **提案模式（默认）**：列出命中 + 建议改写，不动文件。
- **编辑模式**（用户要求改时）：应用改写，然后重新扫描确认。

## 起手定位

种子模式只**定位候选**，不判定命中。每个候选必须逐句过下面的「判定门」才可能算命中：

`本流程|本 ?skill|这个 ?skill|本文档|本节|把自己当作|结对|不是.*而是|不从.*开始|并非|不属于|仔细|适当|按需|合理|高质量|健壮|重要的是|需要注意|值得一提|总之`

「重复事实来源」grep 抓不到，靠跨文件判断：写规则前先搜 CLAUDE.md/README/相邻文档有没有已定义。

## 判定门（每个候选先过这两关，才可能算命中）

1. **行动测试**：抛开措辞，这句有没有让读者改变某个具体动作？——「不要做某动作」也算行动约束。**有动作 → 不报。**
2. **豁免测试**：它在不在下方「豁免清单」？**在 → 不报。**

两关都"否"才算命中。**宁可漏报，不可误报**——误报淹没真问题、消耗信任。不确定的标 `LOW?` 交用户定，不要直接当问题。只判措辞可执行性，不提架构/设计意见。

## 反模式（每类带"报 / 不报"判别）

1. **自我指涉 / 免责** — 讲"本文档/本 skill 是什么、不包含什么"且不带动作。
   - 报：「本流程不包含特定框架规则」「这个 skill 是…」
   - **不报**：操作性规则（「默认不进入 TDD 模式」「命中条件才委派」）、一行定向开场（「X 是一条流水线：先…再…」）——带动作或为读者指路。
2. **persona 开场** —「把自己当作资深工程师…」角色扮演、无动作。
3. **否定 / 对比定义** — 用否定描述身份/结构：「X 不是 A，而是 B」「不从 X 开始」。
   - **不报**：禁止具体动作的「不要 commit / 不要 push / 不要 throw / 不要预设框架」——行动约束，过第 1 关。
   - 改：「流水线不是从读 repo 开始」→「流水线从理解用户输入开始」。
4. **空洞限定词** —「适当/合理/高质量/健壮」等在本上下文给不出可执行判据的词。
   - **不报**：领域术语，或紧跟具体判据的词（「合理超时（≤3s）」）。
   - 改：「适当处理错误」→「对外部调用失败返回降级值并记日志」。
5. **填充开场** —「重要的是…/需要注意…/总之…」不带指令的引子。改：删引子留动作。
6. **重复事实来源** — 抄 CLAUDE.md/README/代码/相邻文档已有内容。改：指向 owner，一个概念一处定义。

## 豁免清单（整类不审，命中也不报）

- **可执行禁止项**：「不要 commit/push/throw/预设框架」——动作约束。
- **delegate prompt 正文**（`prompts/` 下、整段喂给子代理的文件）：里面的「而不是」对比、「不要…」护栏是 prompt engineering，**整文件豁免**，不逐句审。
- **操作性规则 / 一行定向开场**：带动作或为读者指路的，即使形如"是什么"。
- **领域术语**：有明确业务含义的词，不当空洞限定词。

## 每条改写过四关

| 关 | 要求 |
|---|---|
| 正向 | 说「是什么/做什么」，不说「不是什么」 |
| 可执行 | 改变读者的动作，不只是补全描述 |
| 无损 | 原句的有用信息不丢；没用就删 |
| 最小 | 不加新概念、不加流程 |

任一关不过：要么删该句，要么重写到过关。

## 循环停止条件

改写后重新整扫一遍——改写本身可能带进新的反模式。连续一次完整扫描零命中才停。

## 输出格式

提案模式，逐条：

```
命中：<file:line>
类型：自述免责 / persona / 否定对比 / 空洞限定词 / 填充开场 / 重复来源
理由：<为什么不可执行>
改写：<正向可执行版本>
```

编辑模式：逐条应用后附 `重扫：N 处 → 0`。

零命中：`无自述型反模式`。

## 指导原则

每一句靠「改变读者做什么」挣得它的位置。描述文档自己的句子挣不到。
