# 可执行指令审查

指令文档的每一句都要指导读者「做什么 / 是什么 / 何时做」，并遵守文档主语言。揪出只描述文档自身、不产生动作的句子，以及可本地化的外语说明混入主语言正文的问题，改写成正向可执行、语言一致的指令，循环到一次完整扫描零命中。

## 审查—改写循环

```
扫描 → 标记命中 → 改写成正向动作 → 重新扫描 → 零命中才停
                          └──── 改写可能引入新的自述 ────┘
```

## 模式

- **提案模式（默认）**：列出命中 + 建议改写，不动文件。
- **编辑模式**（用户要求改时）：应用改写，然后重新扫描确认。

## 起手定位

种子模式只**定位候选**，不判定命中。每个候选必须逐句过下面的「判定门」才可能算命中：

`本流程|本 ?skill|这个 ?skill|本文档|本节|把自己当作|结对|不是.*而是|不从.*开始|并非|不属于|仔细|适当|按需|合理|高质量|健壮|重要的是|需要注意|值得一提|总之`

中文文档里的拉丁字母混用候选用这个命令定位，只当候选，不直接报：

```bash
rg -n "[\u4e00-\u9fff].*[A-Za-z]{4,}|[A-Za-z]{4,}.*[\u4e00-\u9fff]" <path>
```

「重复事实来源」grep 抓不到，靠跨文件判断：写规则前先搜 CLAUDE.md/README/相邻文档有没有已定义。

## 判定门（每个候选先过这两关，才可能算命中）

1. **行动测试**：抛开措辞，这句有没有让读者改变某个具体动作？——「不要做某动作」也算行动约束。**有动作 → 不报。**
2. **豁免测试**：它在不在下方「豁免清单」？**在 → 不报。**

两关都"否"才算普通指令反模式命中。语言混用候选单独过「语言一致性门」。**宁可漏报，不可误报**——误报淹没真问题、消耗信任。不确定的标 `LOW?` 交用户定，不要直接当问题。只判措辞可执行性和说明性正文的语言一致性，不提架构/设计意见。

## 语言一致性门（只审说明性正文）

先判断文档主语言：看用户要求、团队语言政策、文件已有主体语言和目标读者。主语言是中文时，普通说明性正文里可中文化的英文要报；主语言是英文时，反向检查可英文替换的中文说明混入。其他语言同理：只审偏离主语言的普通说明词，不审专名和领域术语。

**报**：外语只是普通流程词、动作词、说明词、占位词或泛化标签，本地化后不会破坏专名、引用、字段匹配或搜索价值。

- `quick check` → `快速检查`
- `follow up` → `后续跟进`
- `owner` → `负责人`
- `risk level` → `风险等级`
- `source gate` → `来源关卡`
- `scratch pad` → `任务记录`
- `finding(s)` → `发现项`
- `triage` → `分诊`

**不报**：外语承担专名、标准术语、契约值、字段匹配、引用原文或跨系统检索价值。

- 人名、机构名、品牌名、产品名、项目名、会议名、证书名、法规名、标准名，如 `OpenAI`、`Salesforce`、`GDPR`、`SOC 2`
- 指标、模型、行业缩写、专业术语、药品名、法律定义项、财务科目，如 `ARR`、`NPS`、`SKU`、`EBITDA`、`Data Processor`
- UI 标签、表头、字段名、配置 key、状态枚举、路径、命令、代码、API/库名、协议名、错误名
- 直接引用、合同定义、客户原话、源材料原文、必须和外部系统完全匹配的字符串
- 用户明确要求保留的术语，或当前文档/相邻文档已有 glossary 定义的术语

输出时说明为什么该外语片段属于可本地化说明正文，而不是专名、术语、引用或契约标识。

## 反模式（每类带"报 / 不报"判别）

1. **自我指涉 / 免责** — 讲"本文档/本 skill 是什么、不包含什么"且不带动作。
   - 报：「本流程不包含特定框架规则」「这个 skill 是…」
   - **不报**：操作性规则（「默认不进入 TDD 模式」「命中条件才委派」）、一行定向开场（「X 是一条流水线：先…再…」）——带动作或为读者指路。
2. **persona 开场** —「把自己当作资深工程师…」角色扮演、无动作。
3. **否定 / 对比定义** — 用否定描述身份/结构：「X 不是 A，而是 B」「不从 X 开始」。
   - **不报**：禁止具体动作的「不要 commit / 不要 push / 不要 throw / 不要预设框架」——行动约束，过第 1 关。
   - 改：「流水线不是从读 repo 开始」→「流水线从理解用户输入开始」。
4. **空洞限定词** —「适当/合理/高质量/健壮」等在本上下文给不出可执行判据的词。
   - **不报**：领域术语，或紧跟具体判据的词（「合理超时（≤3s）」）。
   - 改：「适当处理错误」→「对外部调用失败返回降级值并记日志」。
5. **填充开场** —「重要的是…/需要注意…/总之…」不带指令的引子。改：删引子留动作。
6. **重复事实来源** — 抄 CLAUDE.md/README/代码/相邻文档已有内容。改：指向 owner，一个概念一处定义。
7. **语言混用** — 主语言正文中混入可本地化的普通外语说明。
   - 报：「先做 quick check，再安排 follow up」「固定从 prompts/business-analyst.md 启动 source gate」「创建 scratch pad」
   - **不报**：「适用于 GDPR 相关请求」「同步 Salesforce 字段」「返回 `ENTER_PIPELINE`」「运行 `git diff --check`」「引用客户原话 `Need a refund`」
   - 改：「source gate 通过后创建 scratch pad」→「来源关卡通过后创建任务记录」。

## 豁免清单（整类不审，命中也不报）

- **可执行禁止项**：「不要 commit/push/throw/预设框架」——动作约束。
- **delegate prompt 正文**（`prompts/` 下、整段喂给子代理的文件）：里面的「而不是」对比、「不要…」护栏是 prompt engineering，豁免自述、否定对比和禁止项审查；**不豁免语言混用审查**。
- **操作性规则 / 一行定向开场**：带动作或为读者指路的，即使形如"是什么"。
- **领域术语**：有明确业务含义的词，不当空洞限定词。
- **专名、术语和契约值**：人名、机构名、产品名、法规名、标准名、指标名、领域术语、状态枚举、字段名、路径、命令、配置 key、role 名、API 名、库名、协议名、错误名。

## 每条改写过四关

| 关 | 要求 |
|---|---|
| 正向 | 说「是什么/做什么」，不说「不是什么」 |
| 可执行 | 改变读者的动作，不只是补全描述 |
| 无损 | 原句的有用信息不丢；没用就删 |
| 最小 | 不加新概念、不加流程 |

任一关不过：要么删该句，要么重写到过关。

## 循环停止条件

改写后重新整扫一遍——改写本身可能带进新的反模式。连续一次完整扫描零命中才停。

## 输出格式

提案模式，逐条：

```
命中：<file:line>
类型：自述免责 / persona / 否定对比 / 空洞限定词 / 填充开场 / 重复来源 / 语言混用
理由：<为什么不可执行或为什么属于可中文化说明性正文>
改写：<正向可执行或语言一致的版本>
```

编辑模式：逐条应用后附 `重扫：N 处 → 0`。

零命中：`无指令/正文反模式`。

## 指导原则

每一句靠「改变读者做什么」挣得它的位置。描述文档自己的句子挣不到。
