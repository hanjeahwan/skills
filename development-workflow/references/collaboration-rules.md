# 协作规则

主流程要求处理委派或规则沉淀时，先执行主文件硬门槛，再使用下列规则。

## 并行审查与验证

将子代理作为状态机执行体管理：启动前定义目的、等待点、影响范围与等待策略。调用宿主能力时保留触发语义：`spawn subagents` / `delegate` / `subagent workflows` / `parallel agent work`。

可在不改变本轮交付物模式的前提下启动子代理，用于受限并行审查、独立验证，或拆分默认串行的任务。它不得绕过交付物判断、先出方案再实现规则、只读约束或等待确认条件；未触发这些条件时，无需每次确认。委派仅补充主线程判断，最终取舍仍由主线程负责。

- 适用场景：多模块、状态流、外部 contract、side effects、权限/数据流、用户可见行为的重构；跨模块或跨边界改动；敏感工作流、安全/权限/数据流风险；代码/diff 审查、独立验证；以及边界清晰、可拆分的实现任务。
- 启动前区分主线与旁路：主线程负责设计判断、用户沟通、diff review、合并顺序与最终验证；委派任务只处理独立、可验证、不会替代主线程判断的部分。
- 委派任务必须包含清晰输入、目标、范围、输出格式与读写边界。代码修改类任务需指定可读文件、可写文件、参考模式、验证入口和结果格式，并提醒执行者不得 revert、stage、commit、push 或覆盖他人改动。
- 实现类拆分任务默认串行；未满足子代理写入边界时，并行仅用于只读审查或独立验证。
- 委派前做冲突检查：确认任务不会覆盖用户已有改动，不会与主线程正在编辑的文件、生成物、测试环境、开发服务器、缓存目录或其他运行时资源冲突；有冲突则留在主线程串行处理。
- 使用 subagent tool 或其他 delegation 工具前，先确认当前平台支持该工具、不会递归进入同类 sandbox，且用户或项目配置允许；否则降级为本地二次审查或串行执行。
- 不适合委派的任务留在主线程：强耦合设计判断、紧急阻塞问题、需要连续用户交互的流程，或结果必须由当前上下文直接决定的工作。
- 若当前环境无可用并行审查、独立验证或委派工具，或平台规则不允许本次调用，则执行本地第二轮审查或串行执行，并在最终回复说明未使用委派的原因。

## 子代理写入边界

默认子代理只读。允许写入必须同时满足这些条件：

- 当前任务已经进入实现模式。
- 主线程已经分配 disjoint write set。
- 主线程先做 `git status --short` 快照。
- 不共享同一文件、同一生成物、同一测试环境、同一开发服务器、同一缓存目录或同一 runtime resource。
- 委派 prompt 明确可读范围、可写文件、禁止改动范围、参考模式、验证入口、输出格式、不得 revert/stage/commit/push、不得覆盖他人改动。

高风险任务默认不得委派写入。只有主线程明确 disjoint write set、禁止外部状态操作、验证命令和合并顺序时，才允许写入委派。

主线程负责 review diff、冲突处理、整体验证和最终交付。子代理结果只作为输入，不自动采纳。

## 不确定边界必须询问

当需求包含“所有、任何、全局、当前流程、保持不变、不影响其它范围、接管、替换、禁用、压制、恢复、重试”等宽范围词时，先拆分语义分区。

如果存在任一分区满足以下条件，必须先问用户，不能自行补默认结论：

- 旧机制会被禁用或压制，但新机制只明确覆盖部分分区。
- 用户要求的目标行为只在部分分区有证据成立。
- 某个分区是否属于目标范围，会改变 UI、数据、错误处理、状态流、权限或副作用。
- 恢复前态无法从代码、类型、测试、文档或用户原话证明。
- “保持不变”和“接管/替换/压制”同时出现，但覆盖范围不等价。

只有代码、类型、测试、文档或用户原话能证明边界时，才可以继续执行。不能用“看起来合理”“通常如此”“主路径如此”代替授权。

询问时只问会改变执行结果的最小问题，并给出推荐选项和失败后果。

## 规则沉淀（任务结束前）

若用户纠正，或 review/测试/子代理结果暴露出反复出现的决策偏差，应将其固化为**让下次默认做对**的持久规则，而不是一次性补丁。

- **提炼根因，不记流水账**：追问“什么原则本可避免这次偏差”，将具体事故抽象为可复用判断，不记录某文件某行这类一次性细节。
- **找对事实来源**：先判断规则归属哪个已有文档/约定/skill；读取后优先改写或合并进去，不另起重复段落。一个概念只放一处。
- **过四关再落**：必须同时满足可泛化、最小、连贯、可执行；即适用未来多次任务、不引入冗余流程、契合既有结构术语，并能改变下次决策。任一不满足则不固化。
- **没有合适拥有者时**，才创建最小新落点。
- **验证**：改完重读相关段落，确认无重复、矛盾、难定位，且不与既有拥有者冲突。

目标：不优化“记住过去”，优化“下次默认做对”。

## 规则沉淀授权门

任务结束前只做“是否需要沉淀”的判断。

- 只读、分析、review、审批、`plan only`、`review only`、`explain only` 任务：只在最终回复提出规则建议，不写文件。
- 只有用户明确要求更新规则，或本轮交付物本来包含规则、skill 或指令文件修改，才允许落盘。
- 落盘前先找拥有者：AGENTS.md、README、docs、当前 skill 或 references；优先改现有 owner，不另起重复段落。
- 落盘后重读相关段落，确认无重复、无矛盾、触发条件清楚，且不会越过当前交付模式。
