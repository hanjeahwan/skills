# 交付执行细则

主流程要求加载交付细则时，按对应分支执行；未在当前任务触发的分支不用加载。

## 调试规则

- 不要脑补根因。先复现、追踪数据流，或对照日志/调用链验证。
- 用户指出 demo、相邻实现或历史行为时，先比较差异，再下结论。
- 只加窄诊断；确认原因后，决定移除还是保留。
- 用户观测和假设冲突时，丢掉假设，重新检查工作流。
- 对异步流程要追真实顺序：event emission、side effect、state transition、finalize、retry path。
- 修 bug 前先判断它属于哪个 phase 或边界，避免在错误层修症状。

## 代码审查模式

- 用户说 `review`、`code review`、`看 diff`、`审这个 PR` 或类似请求时，默认只审查，不修改文件。
- 输出先列发现项，按严重度排序；不要把总结放在问题前面。
- 每个发现项要包含文件/行引用、具体故障模式、影响对象、何时会爆发，以及建议修法。证据不足时说明不确定性，不要编造。
- 优先找行为回归、安全/权限问题、数据损坏、并发/异步问题、contract 破坏、缺失验证；避免低价值风格意见淹没真正风险。
- 如果没有发现问题，明确说没有发现阻塞项，并说明剩余测试缺口或残余风险。

## 验证工具边界

- 自动化测试只使用当前项目已经存在、可维护、能被本次变更执行路径触达的 test harness。
- 项目没有 test harness、测试命令或测试目录时，不要为了本次任务新增测试框架、测试依赖、测试配置或大块测试脚手架。
- 需要新增测试体系本身时，先作为单独方案说明成本、维护负责人和迁移路径，等用户确认后再做。

## Test-Driven Development

- 只有用户明确要求 TDD、test-first、red-green-refactor、integration tests，且当前项目已有可维护 test harness 时，才进入 TDD 模式。任务行为风险高且当前项目已有可维护 test harness 时，也可进入 TDD 模式。
- 如果当前项目已有明确的 TDD 流程、测试命令或测试工具链，优先按项目方式执行 red-green-refactor。
- 如果已有可维护 test harness，但没有明确的项目 TDD 流程，按轻量 TDD 协议执行：一次只写一个测试，只测 public interface 的可观察行为，先 RED，再写最小实现到 GREEN，全部通过后才 refactor。
- 不要 horizontal slicing：不要一次写完所有测试再实现。
- 如果行为 contract 已清楚，直接列出第一个要验证的行为并实现一个最小可验证路径；如果不清楚，只问一个关键问题。
- 如果项目没有可维护 test harness，不进入 TDD；说明测试缺口，按验证选择矩阵改用现有静态检查、现有验证命令或手动路径验证。

## 实现规则

- 以当前项目认可的核心领域对象作为唯一事实来源。不要为了方便镜像成多个平行属性，除非它们有独立 lifecycle 或缓存价值。
- 不要加 getter/setter 做简单派生。
- 避免冗余 props、冗余 methods、冗余 snapshots；已有函数或组件能表达同一数据时直接复用。
- 不要为了防御理论上不存在的状态到处 throw error；先确认现有工作流是否保证数据存在。
- 类型和接口默认靠近使用点；只有跨边界共享时才 export。
- 命名要表达 domain，不要用泛化或测试语义污染业务概念。
- boolean flags 用 domain predicate 前缀：`is...`、`has...`、`can...`、`should...`。
- 符号命名要有明确作用域但不冗余；目录或 feature 已表达的上下文，不要在文件名和类型名里重复堆叠。
- 当流程出现多个阶段、用户事件、异步 side effects、retry、terminal states，或多个 boolean 互相推断时，先用 state machine 思路建模：列出 states、events、transitions、guards、effects 和不可达状态。默认先作为分析和重构方案，不要直接引入状态机库。
- 如果现有实现已经因为 boolean 组合、分支散落或副作用顺序导致维护风险，建议用户把实现重构成 state machine like 结构，例如 reducer、transition table 或 state controller；优先沿用当前仓库的状态管理工具，只有仓库已有状态机实践或复杂度明确需要时，才考虑引入状态机库。
- 保持 phase boundaries。不要把用户动作、入口校验、刷新/重载、运行期副作用、persistence、交互策略混在一起，除非任务明确包含。

## 技术文档更新

- 文档变更先找事实来源：代码、types、schemas、tests、README、docs、ADR 或用户点名文件。
- 写文档时描述当前系统真实行为和决策边界，不要把愿望、未实现功能或临时猜测写成事实。
- 如果代码和文档冲突，先指出冲突并按任务目标处理；不能确认时保留不确定性，不要静默二选一。
- 文档改动也要验证：检查链接、命名、命令、文件路径和示例是否仍然对应当前仓库。

## 范围与恢复完整性审计

当需求包含接管、禁用、替换、保持不变、恢复、重试、不影响其它范围、不要使用某机制或不要改变某契约时，先完成本审计，再输出完整方案。

未证明分区覆盖、机制接管和恢复前态前，只能把方案标为草案或缺口方案。

### 范围和分区

先提取目标范围、排除范围、保持范围、失败范围、恢复范围、禁止机制和契约边界。

再枚举分区：入口、模式、权限、开关、数据差异、生命周期、事件来源、成功/失败、能力存在/不存在/部分存在/不支持/不适用但流程仍运行。

不能把“不适用某能力”当成“不进入流程”。只有代码、路由、状态或数据契约证明不会进入，才能排除。

### 覆盖矩阵

凡是关闭旧机制、压制旧 UI、替换旧状态流、接管错误处理或新增恢复流程，必须列矩阵：

| 分区 | 原机制覆盖 | 新机制覆盖 | 保留机制 | 结论 |
| --- | ---: | ---: | --- | --- |

规则：

- 原机制覆盖而新机制不覆盖时，必须有保留机制。
- 没有保留机制就是缺口。
- “保持不变”“不影响其它范围”“所有/任何/全局/当前流程”必须拆成矩阵行。
- 只写主路径不算通过。

### 恢复和副作用

凡是涉及恢复、继续、重试、保留进度或不要重复触发，必须列出：

| 中断前状态 | 中断事件 | 中断后状态 | 恢复目标 | 可重复副作用 | 禁止重复副作用 |
| --- | --- | --- | --- | --- | --- |

已经发生过的提交、确认、上传、通知、导航、计时器、状态事件不得重复触发，除非需求明确允许。

如果无法区分中断前态，不得用一个通用恢复动作覆盖全部分区。

### 禁止机制和错误分类

当用户要求不要使用某机制时，检查直接和间接路径：它由哪些入口、状态或副作用触发，压制后由谁接管，非目标分区是否保留，是否仍有间接路径改变状态。

当需求改变失败处理时，至少区分可恢复、不可恢复、权限/认证、业务/校验、远程服务、本地能力、后台任务和用户前台错误。

输出方案时先给覆盖结论；有缺口就标缺口，不要写成完整方案。

## 重构准备清单

涉及多个模块、状态流、外部 contract、side effects、权限/数据流或用户可见行为的重构前，准备这些内容：

- **当前工作流**：入口、分支、terminal states、side effects。
- **问题**：具体 bug、维护性问题或行为风险。
- **状态质量**：非法状态、重复状态、派生状态、单一事实来源，以及 boolean 组合是否会漂移。
- **事件审查**：逐个 event/action 列出允许状态、禁止状态、no-op 行为、missing guard、terminal behavior，以及 guard 与 tests/docs 是否一致。
- **副作用归属**：每个 side effect 由谁触发、何时触发、成功/失败事件如何回到状态流。
- **方案边界**：状态模型、service 边界、public API 保持/拆分边界或归属。
- **范围**：会改哪些文件，哪些文件明确不改。
- **行为保持**：哪些现有行为必须不变。
- **文档影响**：仓库指令文件、README、docs、ADR、用户点名的规范文件、技术说明是否需要同步；只记录真实已实现行为，不把计划写成事实。
- **验证计划**：按验证选择矩阵选择入口。
- **高风险确认**：命中高风险触发条件时，按风险关卡列出需要确认的点。

## YAGNI

- 不要为了未来可能的需求提前抽象、提前扩展或提前预留入口；只有当前需求已经明确需要，或现有代码已经出现真实重复和维护成本时，才引入抽象。
- 不要提前设计可配置化、插件化、策略模式、通用工具层或中间适配层；除非当前已有两个以上真实使用场景，并且差异边界清晰。
- 不要为了“以后可能会用”保留未使用的 props、参数、字段、分支、状态、组件、方法或类型；未被当前流程消费的内容不要实现。
- 不要把单一业务场景泛化成通用框架。先用当前 domain 的直接表达实现，等重复模式稳定后再抽象。
- 不要为理论上的扩展牺牲当前代码的可读性。当前业务路径清晰、数据来源明确、阶段边界稳定，优先于“看起来更灵活”。
- 发现可以做但当前需求没有要求的能力时，记录为后续方案或待办项，不能混入本次实现。
- 删除比保留更符合 YAGNI：如果某段代码没有当前调用方、没有明确生命周期、没有测试覆盖的业务价值，应优先移除，而不是继续维护。

## 验证选择矩阵

- 先按验证工具边界选择已有工具；没有 test harness 时不要为了验证临时搭测试体系。
- 行为改动：已有 test harness 能覆盖该行为时，优先跑定向测试；没有测试时做手动路径验证并说明缺口。
- 类型、schema、API contract 改动：跑 typecheck 或最接近的静态检查，并检查调用点。
- 高风险改动：先按风险关卡列出的风险面和确认门选择证据入口，例如当前项目已有测试、typecheck、迁移 dry-run、本地运行、日志/审计检查、手动路径或截图/交互检查；无法验证时按风险关卡记录未验证风险缺口。
- 复杂 UI 改动：按风险选择本地运行、截图/交互检查、移动端或关键断点检查、手动路径验证、可访问性或视觉回归检查；已有可维护 UI test harness 时才补自动化 UI 测试。
- 构建产物或打包产物是本次交付物时：才跑 `build` 验证产物是否能生成；其它改动默认不跑 `build`。
- 文档改动：用事实来源对照关键命令、路径、术语和示例，不用为了纯文档默认跑全量测试。
